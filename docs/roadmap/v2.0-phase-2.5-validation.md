## Recovery model

On every authenticated startup, reload, token recovery, or account event, the UI returns to local authority while migration state is rebuilt. The client reads the exact owner receipt and current cloud tracker, then computes a fresh canonical cloud checksum. A receipt suppresses migration review only after this fresh read succeeds. Keep Cloud suppression additionally requires a marker derived for the current account and the current selected-source checksum.

An RPC response is never durable client evidence by itself. If transport completion is uncertain or post-operation verification is interrupted, local authority remains active and a new state inspection determines whether a receipt now exists and whether the current cloud tracker can be read safely. Retry review therefore uses new cloud checksums and revisions.

## Deferred boundaries

- Phase 2.6 adds ordinary cloud show/season writes and revision-conflict editing. Phase 2.5 has no cloud-write repository and no offline write queue.
- Phase 2.7 adds the server-side TMDB Edge Function and hosted deployment work.
- Restore-v2 UI, production/staging projects, hosted Auth configuration, remote linking/deployment, and production release remain deferred.
