# TV Series Tracker v2.0 — Supabase Cloud Persistence Roadmap

**Status:** Active planning  
**Milestone:** v2.0  
**Target:** GitHub Pages frontend with Supabase Postgres, Auth, and Edge Functions  
**Owner:** TV Series Tracker maintainers  
**Last updated:** 2026-08-17

## 1. Goal

TV Series Tracker v2.0 replaces device-only LocalStorage persistence with a private, authenticated Supabase backend. The same tracker must be available across desktop, phone, and tablet without losing the existing 352-show catalogue, per-season progress, artwork references, or JSON backup capability.

The authoritative data model is defined in [`../architecture/SUPABASE_DATABASE_CONTRACT_V2.md`](../architecture/SUPABASE_DATABASE_CONTRACT_V2.md). If this roadmap and the contract disagree, the contract takes precedence.

## 2. Delivery principles

- Follow the established TTSPlayer cadence: **plan → document → implement → validate → close**.
- Treat every phase as a reviewable mini-release with an explicit definition of done.
- Use version-controlled Supabase migrations; do not make undocumented production-only schema changes.
- Keep Supabase as the cloud source of truth after migration.
- Retain LocalStorage as a migration source, temporary cache/fallback, and rollback copy until cloud validation succeeds.
- Keep JSON export and restore as user-visible backup capabilities.
- Never expose a Supabase service-role key, database password, TMDB token, or other secret in GitHub Pages.
- Preserve private per-user ownership through Supabase Auth and Row Level Security.
- Avoid unrelated features and unnecessary personal data.
- Do not begin a later phase until the current phase's mandatory acceptance checks pass or any exception is explicitly documented.

## 3. Target architecture

```text
Desktop ─┐
Phone ───┼──> GitHub Pages application
Tablet ──┘              │
                         ├──> Supabase Auth
                         ├──> Supabase Postgres
                         │      ├── shows
                         │      └── season_progress
                         └──> Supabase Edge Function ──> TMDB

LocalStorage: migration source and bounded fallback/cache
JSON export: user-controlled backup and restore
```

The initial v2.0 ownership model is one private tracker per authenticated user. Shared or household trackers are deferred.

## 4. Phase overview

| Phase | Name | Primary outcome | Status |
|---|---|---|---|
| 2.1 | Architecture and planning baseline | Approved specifications, ADRs, security model, and implementation sequence | Complete |
| 2.2 | Supabase foundation | Reproducible project configuration and migration workflow | Next |

| 2.4 | Import infrastructure and validation | Transactional import/reconciliation design and verified test imports | Not started |

## 5. Phase 2.1 — Architecture and planning baseline

### Objective

Create the version-controlled specifications needed to implement v2.0 without relying on chat history or undocumented assumptions.

### Deliverables

- [Supabase database contract](../architecture/SUPABASE_DATABASE_CONTRACT_V2.md).
- v2.0 roadmap (this document).
- [RLS and mutation-function specification](../database/rls-and-mutation-functions.md).
- [LocalStorage-to-Supabase migration specification](../database/localstorage-migration.md).
- [Initial 352-show import specification](../database/initial-352-show-import.md).
- [ADRs](../README.md#architecture) covering Supabase as source of truth, private ownership, Auth/RLS/RPC, LocalStorage migration, optimistic concurrency, and server-side TMDB access.
- [Phase 2.1 validation checklist](v2.0-phase-2.1-validation.md) and definition of done.

### Validation and exit criteria

- Documentation agrees with the current v1 data shape and status vocabulary.
- The model uses private user-owned `shows` and `season_progress` rows plus private migration infrastructure.
- Required specifications and ADRs are reviewed and accepted.
- Phase 2.2 can proceed without inventing architecture decisions.

## 6. Phase 2.2 — Supabase foundation

### Objective

Establish a minimal, reproducible Supabase development foundation without importing production data.

### Deliverables

- Supabase project in the agreed region.
- Version-controlled `supabase/` structure and ordered migrations.
- Local development and deployment workflow.
- Browser-safe configuration separated from secrets.
- Configuration example committed; credentials excluded.
- Environment boundaries and rollback/forward-migration conventions.

### Validation and exit criteria

- A clean checkout can reproduce the local database workflow.
- Ignore checks prove secrets are not tracked.
- GitHub Pages receives only the project URL and publishable/anon key.
- The empty foundation can be reset and recreated safely.

## 7. Phase 2.3 — Database schema and RLS

### Objective

Implement the database contract through migrations and prove ownership isolation before application integration.

### Deliverables

- `season_status`, `shows`, `season_progress`, and private `migration_receipts` migrations.
- Contract-defined constraints, indexes, cascades, server-managed timestamps, and revisions.
- Server-owned `revision` fields and optimistic-concurrency primitives.
- Forced RLS with authenticated owner-scoped reads.
- Dedicated `NOLOGIN`, non-`BYPASSRLS` `tracker_api_owner` function owner, least-privilege grants, and owner-scoped forced-RLS write policies.
- Direct domain `INSERT`, `UPDATE`, and `DELETE` revoked from browser roles.
- Narrow security-definer mutation-function contracts, exact input/result schemas, safe fixed `search_path`, captured caller authentication, and restricted execute grants.
- Client-adapter normalization of database results versus session/gateway authorization failures.
- Anonymous access revoked.
- Automated schema and RLS tests.

### Validation and exit criteria

- User A cannot read or mutate User B's rows or attach seasons to User B's shows.
- Anonymous requests cannot access domain rows.
- Authenticated browser roles cannot perform direct domain DML or forge ownership, timestamps, or revisions.
- The function owner cannot log in, bypass RLS, exceed exact grants, or access rows owned by a different `auth.uid()` context.
- Anonymous execute is denied; client `unauthenticated`/`forbidden` results come from safe adapter normalization rather than function grants.
- Expected-revision update/delete tests prove atomic conflict detection and stable conflict results.
- Invalid and duplicate data fails cleanly.
- Show and Auth-user deletion cascades correctly.
- Migrations reproduce the contract on an empty database.

## 8. Phase 2.4 — Import infrastructure and validation

### Objective

Design and prove the idempotent, lossless import/reconciliation infrastructure for the existing 352-show tracker and every season status. This phase uses controlled test identities; it does not run the real browser/user migration before application Auth exists.

### Deliverables

- Validators for baseline JSON/JS and `tvSeriesTrackerData.v1`, including the current nested `tmdb` object and supported aliases.
- Explicit v1-to-v2 mappings, precedence rules, and contradictory-TMDB reporting.
- Transactional import/reconciliation function design and controlled implementation boundary.
- Atomic dry-run/report mode using controlled test identities.
- Idempotent show and season upserts.
- Exact replacement semantics, including removal of absent shows and shortened/absent seasons within tracker scope.
- Non-destructive reviewed-merge semantics with explicit approval for deletions.
- Final show-count, season-count, and deterministic checksum/equivalent verification.
- Private cloud migration-receipt design and transactional write behaviour.
- Rollback/export procedure and non-authoritative local device marker.

### Validation and exit criteria

- All 352 shows import under controlled test identities without loss or duplication.
- Re-running import creates no duplicates.
- Metadata and all five season states round-trip.
- Invalid input cannot cause a partial import.
- Nested TMDB metadata and independent `posterUrl` preservation match the current application shape; contradictory IDs fail with a report.
- Replacement produces an exact verified snapshot, while merge retains absent rows unless deletion is explicitly approved.
- A receipt is created only for a committed, verified migration and is private to its test owner.
- Phase 2.5 can invoke the proven migration path after minimum Auth/session establishment.

## 9. Phase 2.5 — Auth, end-user migration, and cloud reads

### Objective

Introduce minimum Auth/session establishment, inspect authoritative cloud migration state, run or offer the real end-user migration, and only then render the tracker from Supabase without changing its data semantics.

### Deliverables

- Minimal private-app Auth flow with session restore/sign-out.
- Browser-safe Supabase client configuration.
- Authoritative `migration_receipts` lookup after authentication, with the local marker used only for device UX.
- Keep-cloud, exact-replace, or reviewed-merge decision when migration is required and cloud data already exists.
- Real browser/user migration through the Phase 2.4 controlled transactional path before cloud-read cutover.
- Verified rollback export/LocalStorage retention after migration.
- Repository/data-service layer.
- Explicit database-to-client mapping.
- Ordered nested season reads.
- Loading, empty, offline, unauthenticated, and error states.
- Controlled LocalStorage fallback/cache.

### Validation and exit criteria

- Users see only their own tracker.
- A user is authenticated before any owned tracker import, and a verified cloud receipt prevents repeat migration prompts on other devices.
- Failed or cancelled migration does not switch the application to an incomplete cloud tracker.
- A second device reproduces the same cloud data.
- Derived counts/statuses and existing views remain correct.
- Sign-out exposes no prior-user data.
- Failed reads do not silently replace valid cache with an empty tracker.

## 10. Phase 2.6 — Cloud writes and multi-device sync

### Objective

Move all supported mutations to Supabase so it becomes the authoritative writable store.

### Deliverables

- Cloud create, update, delete, and season upsert operations.
- RPC/database-function-only mutations with server-owned ownership, timestamps, and revisions.
- Expected-revision update and delete operations with atomic revision increments.
- Stable conflict results containing safe current owned server state, followed by refresh and user retry/review.
- Server timestamps for committed-version ordering; no timestamp-only stale-write protection.
- Explicit online/offline mutation rules.
- Recoverable UI errors and cache refresh after commits.
- Multi-device and destructive-operation tests.
- v2 JSON export/restore.

### Validation and exit criteria

- Mutations persist after reload and appear on another device.
- Stale clients receive a conflict and do not silently overwrite newer rows.
- Direct authenticated table DML and attempts to forge ownership, timestamps, or revisions fail.
- Failed writes leave recoverable, truthful state.
- Export/restore is equivalent.
- LocalStorage is no longer authoritative after migration.

## 11. Phase 2.7 — Secure TMDB, deployment, and closure

### Objective

Move TMDB behind a trusted server-side boundary, deploy v2.0, validate production, and close the milestone.

### Deliverables

- Supabase Edge Function for TMDB enrichment.
- TMDB secret stored server-side only.
- Input validation, controlled CORS, bounded results, errors, and basic abuse controls.
- Client `Find Artwork` integration.
- Desktop, phone, and tablet validation.
- Production migration runbook, backup, and GitHub Pages configuration.
- Security/RLS/migration/regression evidence and updated release docs.

### Validation and exit criteria

- Browser inspection reveals no TMDB or privileged Supabase credential.
- TMDB matching and poster persistence work in production.
- Auth, CRUD, migration, backup, and multi-device scenarios pass.
- Production migration is verified before LocalStorage loses migration authority.
- No TTSPlayer files, secrets, or infrastructure are involved.
- Release and rollback documentation is complete.

## 12. Cross-phase quality gates

Every implementation phase reports:

1. Scope completed and specification deviations.
2. Files changed and migrations added.
3. Automated tests and results.
4. Runtime validation and environment.
5. Security and secret-handling checks.
6. Documentation updated.
7. Risks, blockers, and deferred work.
8. Commit hash and remaining uncommitted changes.

A phase is not complete merely because code exists. Documentation, validation evidence, and definition of done must agree with implementation.

## 13. Milestone definition of done

v2.0 is complete when:

- the contract is implemented through version-controlled migrations;
- all 352 shows and seasons are migrated without loss;
- Auth and RLS isolate each tracker;
- reads and writes work across supported devices;
- LocalStorage has only a bounded cache/migration role;
- JSON export/restore remains functional;
- TMDB uses a server-side Edge Function;
- desktop/mobile tracker functionality is preserved;
- security, migration, RLS, sync, and regression checks pass;
- authenticated reads and controlled RPC/function mutations obey the documented privilege boundary and optimistic-concurrency contract;
- deployment, release, and rollback documentation is current; and
- TTSPlayer files, secrets, and infrastructure remain completely out of scope.

## 14. Deferred beyond v2.0

- Household sharing and invitations.
- Episode-level progress, history, ratings, notes, recommendations, and social features.
- Multiple platforms and availability history.
- A global shared catalogue.
- Automated TMDB synchronization or cloud image storage.
- Offline mutation queues, tombstones, automatic conflict merging, conflict history, audit history, soft deletion, and analytics.

These require separate specifications and must not be introduced opportunistically during phases 2.1–2.7.
