## Local-only harnesses

[`run-baseline-validation.ps1`](../../supabase/tests/migration/run-baseline-validation.ps1) reads the packaged catalogue in place. It does not copy tracker data into migrations, seed files, or fixtures. It normalizes v1 data, obtains the checksum from the private database helper, exercises migration modes against synthetic identities, verifies owner-scoped state, and removes all synthetic data.

[`run-migration-races.ps1`](../../supabase/tests/concurrency/run-migration-races.ps1) opens independent local PostgreSQL sessions through the local Docker container. A contender submitted before the winner commits necessarily carries the pre-lock checksum; after serialization it must conflict rather than silently reinterpret that stale request. Idempotency is then verified with a retry carrying the committed current checksum. This is the faithful behavior of the accepted checksum-concurrency contract.

Both scripts accept an explicit Docker executable path, target only the local container derived from repository `project_id`, create no persistent fixture data, and clean up synthetic Auth identities and temporary files.

## Deferred boundaries

- Phase 2.5 performs real-user Auth/session establishment, cloud-state inspection, migration choice, browser backup/export, and real-user execution.
- Phase 2.6 integrates cloud reads/writes and synchronization into the application.
- Phase 2.7 implements server-side TMDB access.
- Hosted linking/deployment, real-user data, Auth UI, application integration, Edge Functions, and seed/import data remain outside Phase 2.4 closure.
